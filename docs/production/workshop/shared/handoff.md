# 入力・成果物の受け渡し

**Status: Draft（初期運用契約）**

## 記録の配置

新規作業は `work/<部屋>/tasks/<task-id>/TASK.md` と `runs/<run-id>/RESULT.md` を基本とする。入力・編集・出力・証拠は試行配下の `inputs/`、`working/`、`outputs/`、`evidence/` に分ける。既存のW01レーン・W05 `motions/`等はそのまま使い、記録から参照する。

## 開始と完了

1. 統括担当が目的・受け入れ条件・範囲をTASKへ記録し、Workboardの状態を決める。
2. 実行担当がルート・制作・部屋の規約、関連仕様を読み、入力を固定する。
3. 統括担当が共有資源と担当を確認して実行を割り当てる。既存のGPUキュー・ロックを使う。
4. 実行担当が新しい試行へ成果物とRESULTを残す。別担当の原本を変更しない。
5. 機械検証・対象環境検証・人間レビューを個別に記録する。
6. 統括担当が正本文書への反映先を確認してWorkboardを更新する。次工程は固定された成果物版を参照する。

## 固定する情報

- Git管理入力：コミットとパス。未コミット変更があれば、そのファイルのSHA256も記録する。HEADだけで入力版を表現しない。
- 外部／ローカル入力：取得元、取得日、ライセンス確認、保存先、SHA256。未確認は明記する。
- 出力：ファイル名、形式、版、SHA256、依存テクスチャ、既知の制約。新しい作業IDをゲームのSystem IDとして採用しない。
- 3D：単位、軸、Scale、Pivot、UV、材質・マップ構成。Rig対象は骨格版・親子関係・Rest Pose・Weight。AnimationはMapping・Action・FPS・範囲・Root方針。
- UI：対象画面、状態・操作、基準サイズ、入力方式、Robloxで再実装する要素。
- 再開：試行ID、外部ジョブID、最後の確認状態、残作業、停止理由、次担当。結果不明のジョブを自動再投入しない。

ファイルのハッシュは版の識別であり、生成の完全な再現を保証しない。

## 三つの状態

| 軸 | 正本・値 |
| --- | --- |
| 設計／工程の成熟度 | 各仕様の `Idea / Draft / Designed / Implemented / Unconfirmed` 等。既存Decisionの状態表記は維持 |
| 作業進捗 | Workboardの `Inbox / Needs Human / Ready / Blocked / In Progress / Verify in Studio / Done / Parked` |
| 成果物の受け入れ | RESULTの「未審査／修正要求／用途限定で受け入れ／正式採用／見送り」。判断者・日時・理由・対象版・用途を必ず併記 |

生成成功は受け入れではない。検証Passも正式採用ではない。研究は不採用の結論でも、調査の完了条件を満たせばDoneにできる。検証を担当したエージェントは人間の採用判断を代行しない。

## 保存と共有

既存 `.gitignore` を維持する。記録はGit共有候補、画像・FBX・blend・動画等は既存の除外設定を尊重する。除外された素材は別環境へ自動で届かないため、保存・バックアップ・配布先を決めるまで共有済みと扱わない。実行DB、認証情報、非公開URLは成果物一覧へ載せない。レビューDBの内容を直接変更せず、正式な判断を記録する場合は対象画像版と判断内容をRESULTへ残す。
