# 001: ゲームループとポータル遷移の設計方針

**Status: Draft（草案）**
**Date: 2026-09-25**

## 背景

Anomaly Dungeonの探索を固定階層の進行にすると、到達点と進行方向が自明になりやすい。また、マルチプレイで個人の状態だけが遷移先を支配すると、他プレイヤーが遷移の理由を理解しにくい。

一方で、探索のリスク、経済、Player Anomalyの代償、長期的な知識収集を同じランの中でどう接続するかは、まだ確定していない。

## 現時点の判断

- ランは「依頼 -> 探索 -> 帰還 -> 報酬 -> 換金・強化 -> 次の依頼」を基本循環とする。
- クエストはランの目的、実績・FILE・発見は探索中の知識と長期収集として分離する。
- Secure Slotを通常インベントリとは別の重要資産保護手段として置く案を採る。
- Player Anomalyは原則デバフとし、通常プレイヤーの経済的・ゲーム的な有利さを保つ。その代わり、固有アクションと、ビルドスキルを1回無条件で獲得または強化できる利点を検討する。
- Player Anomalyは1ランにつき最大1人を基本案とし、直接PvPを主目的にしない。
- ダンジョンを固定的な深度ではなく、状態依存のポータル遷移による複数空間のネットワークとして扱う。
- マルチプレイの遷移はParty Stateを用い、特殊条件による確定遷移と状態による確率遷移を組み合わせる。
- プレイヤーには数式を開示せず、FILEと体験から確率の傾向を学べるようにする。

## 理由

- Secure Slotは、死亡がある探索において、何を保護し何を危険にさらすかという判断を作る。
- Player Anomalyを強い恒久的な上位状態にしないことで、通常の協力、経済、帰還をランの中心に残せる。
- 遷移先を完全ランダムにしないことで、探索知識をプレイスキルにできる。同時に結果を完全制御できなくすることで、不確実な空間の探索感を維持できる。
- Party Stateは、平均だけでなく極端なExposureや分布を扱え、マルチプレイそのものを遷移条件の一部にできる。

## 影響

- ポータル解決処理は、個人状態、Party State、特殊条件、候補重みを分けて扱う必要がある。
- クエスト進行とFILE・実績のデータモデルは別にする必要がある。
- Secure Slot、死亡、帰還、アノマリー化は相互に影響するため、実装前に状態遷移を設計する必要がある。

## 未決事項

- アノマリー化中の具体的な帰還方法、および資産利用制約。
- 報酬額、コスト、キル報酬の具体値。
- ExposureとParty Stateの数式、閾値、候補マップと確率。
- 確定遷移条件と、ポータル通過時のパーティ判定。
- ビルドスキルに使う物質、刻み込みの実装・演出・恒久性。
