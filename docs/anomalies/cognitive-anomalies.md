# 認知アノマリー

**Status: Draft（草案）**
**Type: 横断的なアノマリー相互作用設計（Anomaly EntityでもPlayer Anomalyでもない）**

この文書は、プレイヤーが世界を認識する行為そのものをアノマリーとの相互作用にするための設計方針を定義する。個別の認知アノマリーや、認知の変化を伴う Individual Anomaly を確定する資料ではない。

本質は、**プレイヤーが世界を認識するという行為そのものを、アノマリーとの相互作用にする**ことである。

## 概要

認知アノマリーは、怖い映像を見せる、敵を出す、警告HUDを表示するといった単発の演出ではない。プレイヤーが何を見たか、見落としたか、見たものを何だと認識したか、繰り返し観察して認識がどう変わるかを、探索上の入力として扱う。

血、死体、巨大な怪物、グリッチ、突然の音響などの分かりやすいホラー記号は必須にしない。一見普通の背景、遠景、初見では意味を持たない物体、他の物と区別できない対象、「何か違った気がする」程度の変化を使う。プレイヤーが最初からアノマリーと断定するのではなく、観察によって異常性が立ち上がることを目指す。

この方針は[世界観の情報提示方針](../world/information-design.md)にある「ルールは明確、意味は曖昧」に従う。攻略に必要な観察の結果と危険は伝えるが、対象の起源や唯一の正解をHUDで断定しない。

## 設計思想

- 異常を強調しすぎず、背景や差異そのものを観察対象にする。
- 「見えた／見えない」の二値で扱わず、推測、意識的な観察、明確な視認、識別を分ける。
- プレイヤーキャラクターの向きと、ローカル画面で対象を観察していることを同一視しない。
- 観察はボタンを押すだけの正解当てではなく、探索、比較、保持、見直しを伴う行為にする。
- 認知差は便利な答えの表示ではなく、情報の不一致とトレードオフとして扱う。
- 「ANOMALY DETECTED」のような直接警告を基本UIにしない。必要な情報は環境、既存UI、無線、記録などから間接的に示す。

## 認知アノマリーの定義

認知アノマリーとは、対象の物理的な存在だけではなく、プレイヤーが対象を検出し、注意を向け、意味のあるものとして認識する過程に作用するアノマリー、またはその相互作用パターンである。

同じ対象が全プレイヤーに同じように描画される必要はない。ただし、各Clientの見え方が異なることは、共有世界の事実を各Clientが勝手に変更してよいことを意味しない。共有される世界状態と、個人の認識状態を分離する。

## Detect / Observe / Visible / Recognitionの区別

| 段階 | 意味 | 例 | 世界状態を変えるか |
| --- | --- | --- | --- |
| Detect | 痕跡、周辺状況、記録などから存在を推測できる | 遠景の不自然な影、繰り返される音、別の記録 | 原則変えない |
| Observe | プレイヤーが対象へ意識的に注意を向けているとシステムが近似判定する | 画面内にあり、遮蔽されず、一定時間見続ける | 観察進行を更新し得る |
| Visible | 視覚的な対象として明確に認識可能な状態 | 背景との差異、輪郭、挙動が判別できる | 個人表示を変え得る |
| Recognition | 観察・比較などの条件を満たし、対象を識別済みと扱う状態 | 対象の種類ではなく「異常な対象である」と把握する | 条件を満たす場合のみ変え得る |

`Detect` は必ずしも視覚情報ではない。`Visible` でもアノマリーとして意味を理解できない場合がある。`Observe` は視線・画面・遮蔽などの技術的な近似であり、プレイヤーの内心を直接測るものではない。`Recognition` は単一の「見た」フラグにまとめず、必要に応じて個人状態、Party内の共有状態、対象側状態を分ける。

## 遠景観察型アノマリー

遠景観察型は、探索中に背景の一部として存在する対象を、プレイヤーが自ら見出すパターンである。

```text
背景に何かがある
    -> Detect: 差異や痕跡に気付く
    -> Observe: 意図して見続ける／見直す
    -> Visible: 他の背景との差異が増える
    -> Recognition: 対象を異常として識別する
    -> 条件付きの世界状態変化
```

変化は、通常では存在しない経路、ポータル、隠された物品、地図情報、次の探索地点などであり得る。ただし、毎回「正解を見つけたら即報酬」というミニゲームにはしない。完全に識別しなくても帰還でき、観察を続ける理由と危険が同時にある構造を基本候補とする。

## 観察を利用したゲームループ

認知アノマリーは、次の構造を取り得る。

```text
Observe
    -> Identify / Recognition
    -> Reward または世界状態の変化
    -> Exposure / 相手からの認識 / 認知状態変化のリスク
```

観察の報酬候補は、経路の出現、ポータルの出現、隠し物の発見、情報の更新、探索地点の解放である。観察のリスク候補は、Anomaly Exposureの増加、対象からプレイヤーを認識されること、個人の認知状態の変化、他プレイヤーとの情報差である。

報酬とリスクの有無、量、観察を中断した場合の進行保持は個別アノマリーごとに決める。ここで一律の数値、閾値、報酬を確定しない。

## マルチプレイヤーにおける認識差

同じ空間でも、Aには見え、Bには見えず、Aには普通の物に見え、Bには異常として見える状態を許容する。これを単なるClient演出に閉じず、「そこにある」「何もない」というプレイヤー間の会話自体が探索情報になるように扱う。

以下を個別に決める必要がある。

- `Recognition` が個人、Party、世界のどこに保存されるか。
- 一人の識別で共有経路を開くか、複数人の観察を必要とするか。
- 認識差を口頭共有できる情報にするか、共有すると誤解を生む情報にするか。
- 切断、死亡、帰還したプレイヤーの認識状態をどう扱うか。

共有世界の状態変更はServerが決め、Clientは自分が観察できたことと表現を担う。詳細なServer / Client責務は[ゲームルール](../systems/game-rules.md)に従う。

## Individual Anomalyとの連携

認知アノマリーは Individual Anomaly と組み合わせられる。たとえば視認可能な情報量、Visible / Invisibleの対応、他プレイヤーとの差異を変え得る。

[Visible / Invisible Inversion](player-anomalies/visible-invisible-inversion.md)は、同じ共有世界に対する個人の可視性・認識を変える既存Draftである。認知アノマリーはこれを「答えを見せる能力」にはしない。ある情報を得る代わりに通常の情報を失う、見えた対象の意味を誤認し得る、といったトレードオフを残す。

認知アノマリーはPlayer Anomalyそのものではない。また、個別のAnomaly Entityが必ず認知アノマリーである必要もない。Memory Swapperの認識と記憶のずれ、MiWの観察リスクなどとは連携し得るが、それぞれの固有挙動をこの文書で変更しない。

## Robloxでの視認判定方式

### 実現可能な構成

`Workspace.CurrentCamera` は各ClientのローカルCameraであり、Cameraの位置・向き・視野角はServerの共有事実ではない。[RobloxのCamera API](https://create.roblox.com/docs/reference/engine/classes/Camera/CameraSubject)にある `WorldToViewportPoint()` と `ViewportPointToRay()`、`Camera.CFrame`、`ViewportSize` を用い、**LocalScriptで**観察候補を評価する。

観察の候補判定は、少なくとも次の組み合わせを想定する。

1. 対象の代表点または複数のサンプル点が `WorldToViewportPoint()` で画面内か確認する。
2. Cameraの向きと対象方向の角度を使い、視野の中心に近いかを評価する。
3. Cameraから対象へ `Workspace:Raycast()` を行い、対象または対象モデルの一部が最初のヒットかを確認する。
4. 最大距離、最小表示面積、継続観察時間、観察の中断を組み合わせて `Observe` の進行を決める。

Raycastは遮蔽を検証でき、`RaycastParams` でプレイヤー自身や観察用の非衝突装飾を除外できる。[Raycastingの公式資料](https://create.roblox.com/docs/workspace/raycasting)が示すとおり、方向ベクトルの長さが検査距離を決め、`CanQuery=false` のPartは対象外にできる。

### Serverとの境界

画面内か、カメラがどこを向くか、UIに覆われているかはClient固有である。よってServerが「プレイヤーが実際に見た」ことを完全には検証できない。Clientからの観察進行報告は、Serverで少なくとも対象の有効状態、Run参加、対象までの概算距離、進行上限、報告頻度を検証して受理する。

経路開放、報酬、Exposure、共有状態変更などの重要な結果はServerだけが確定する。Clientの一回の通知で即座に重要報酬を与えず、継続時間、複数の観察段階、Server側の前提条件を組み合わせる。

### 技術的制約

- Cameraはローカルであり、Serverがカメラ方向を直接信頼できない。
- `WorldToViewportPoint()` が画面内を返しても、遮蔽、対象の小ささ、UI、プレイヤーの注意までは保証しない。
- Raycastは最初の衝突を返す。対象が大きい、複数Part、Terrain、透明装飾を持つ場合は、対象の代表点・複数点・Query設定を個別に調整する必要がある。
- Instance Streaming使用時、遠方PartがClientに届いていなければRaycastが検知できない。公式資料でもStreaming下のRaycast偽陰性が指摘されているため、遠景観察の対象はStreaming範囲、距離、代替のDetect痕跡を考慮する。
- 毎フレーム、全アノマリーへRaycastしない。Client側で候補を距離・マップ・状態で絞り、観察中だけ必要な頻度で評価する。
- VR、CameraType変更、Spectator的なカメラ、画面比率変更の扱いは未検証である。最初のプロトタイプは通常のデスクトップ／モバイル標準Cameraに範囲を限定する。

## 実装上の注意点

- `Detection`、`Observation`、`Recognition`、世界側の `State Transition`、`Exposure` を一つのBoolや一つのServiceに潰さない。
- 個別AnomalyのServer状態、Client表示、観察判定、Remoteの受理、共有変化を分ける。
- 観察対象の見た目を先に派手にしない。テスト時も、観察がなければ背景として成立するかを確認する。
- HUDで正解や対象名を直接通知しない。目的や危険を明確にする必要がある場合も、対象の正体ではなく行動結果を伝える。
- Client固有の表示だけで共有世界状態を変更しない。逆に、共有状態の変化を全員に同じ意味で見せる必要もない。
- Camera方向だけ、距離だけ、キャラクターの向きだけを `Observe` の唯一の条件にしない。
- `Visible / Invisible Inversion` の実装前提であるComponent分類やClient表示規約を、この資料だけで確定しない。

## 今後のプロトタイプ候補

1. **単一遠景対象の観察計測**: デバッグフロアまたは専用の小規模マップに、背景として成立する対象を1つ置く。報酬を置かず、画面内・遮蔽・距離・継続時間のログだけを検証する。
2. **個人Recognitionの表示差**: 同じ対象に対し、識別前後でClientごとの表示だけを変え、共有世界を変えない。Visible / Invisible Inversionとは独立に検証する。
3. **Server確定の小さな変化**: 観察条件を満たした後、全員が利用できる小さな経路または情報を一つだけ出す。Client通知の改ざん、切断、複数人同時報告を検証する。
4. **Exposureとの接続**: 観察継続でExposureが増える候補を、通常の近接Exposureと混同しない属性・ログで試す。数値や採用は別途決定する。

これらはプロトタイプ候補であり、実装指示ではない。個別アノマリーの名称、外見、報酬、数値、発動条件は未決定である。
