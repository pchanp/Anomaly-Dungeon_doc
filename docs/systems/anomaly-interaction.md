# Anomaly Interaction

> **ステータス: Draft**
>
> この文書は、プレイヤーの既存行動・所持品・環境イベントを、個別アノマリーへの相互作用として接続するための共通設計層を定義する。個別アノマリーの正体や固有挙動は定義しない。

## 目的

アノマリーの追加ごとに専用の検知システムや入力経路を作るのではなく、既存のゲームプレイ行動を意味のある相互作用として再利用できるようにする。

たとえば、あるアノマリーは `Sound Interaction` と `Observation Interaction` を受け取り、別のアノマリーは `Heal Interaction` のみを受け取る。この分類は「有効な攻略手段」を先に保証するものではなく、各アノマリーが何に反応し、どのような状態変化を起こし得るかを明示するためのものとする。

この層の本質は、**既存のプレイヤーアクションを Anomaly Interaction へ接続すること**である。

## 対象としないこと

- すべてのアノマリーに共通する戦闘・撃破ルールの決定
- すべての入力を受理する万能イベントバスの即時実装
- 個別アノマリーのロア、名称、報酬、最終的な攻略法の確定
- クライアント表示だけでアノマリー状態を確定すること
- `Anomaly Entity` と `Player Anomaly` を同じ受信者として扱うこと

`Player Anomaly` はプレイヤー側に発生する状態であり、外部から相互作用を受ける `Anomaly Entity` と同一視しない。必要な連携は個別設計で明記する。

## 基本モデル

```text
Player Action / Item / Skill / Environment Event
                    ↓
           Interaction Context
                    ↓
      Anomaly が受理・拒否・変換・傍受
                    ↓
 State Transition / Result / Feedback / Exposure
```

アクション自体の通常効果と、アノマリーへの追加効果は分離する。たとえば Heal は通常どおりプレイヤーを回復できる一方、対象アノマリーが明示的に `Heal Interaction` を受理する場合だけ、鎮静など別の状態変化を起こせる。

ここでの Interaction Kind は入力の分類である。成立後に何が変わるか、効果の保存境界と重ね掛け・解除の既定規則は[共通Effectと保存境界](effect-components.md)を参照する。

## Interaction Context

個別の相互作用を定義するときは、少なくとも次を記録する。

| 項目 | 内容 |
| --- | --- |
| Interaction Kind | `Observation`、`Sound`、`Heal` 等の意味分類 |
| Initiator | 行為者。プレイヤー、パーティ、環境、別アノマリーなど |
| Target | 対象アノマリーまたは対象状態。対象指定方法も含む |
| Scope | 個人・パーティ・ラン全体のどこに結果が反映されるか |
| Preconditions | 距離、状態、アイテム、地形、時間などの前提条件 |
| Server Validation | サーバーが検証すべき事実と、不正入力時の扱い |
| Result | 状態遷移、通常効果の変換・無効化、情報更新、報酬、Exposure |
| Limits | クールダウン、回数、蓄積、競合時の優先順位 |
| Feedback | 成功・失敗・不明をどう世界内で返すか |

未決定の項目は推測で埋めず、個別資料で `Unconfirmed` として残す。

個別アノマリーがスキル獲得へ接続する場合は、さらに「博士のQuest対象か」「研究対象外のレアアノマリーか」「成立させるInteraction」「出現する一部または関連アイテム」「交換先の専用スキル」「Party配分」を記録する。Quest報告の直接報酬と、相互作用の結果として出現する固有品を混同しない。

## 共通の Interaction Kind

以下は再利用を想定する意味上の分類である。アノマリーは必要なものだけを明示的に受理する。ここにない相互作用を禁止するものではない。

### Observation Interaction

プレイヤーが対象を意識的に観察し、証拠を得ることによる相互作用。`Detect`、`Observe`、`Visible`、`Recognition` の技術的・状態的な区別は [観察・認識システム](observation-and-recognition.md) を正とする。

個別アノマリー側では、どの認識段階で何が起きるか、観察が Exposure や相手側の反応を伴うかを定義する。視界内に入っただけで結果を確定してはならない。

### Sound Interaction

音を発した、聞いた、音源の方向や強度を認識した、といった音に関するゲーム上の事実を入力にする相互作用。

これは実際の音声波形を常時解析することを意味しない。音源の種別、位置、到達範囲、方向、遮蔽、強度など、実装するシステムが提供できる文脈だけを使う。BGM や通常の環境音が自動的に相互作用になるわけではない。

具体的な音の伝播・遮蔽・同期方式は未決定であり、必要になったアノマリーから検証する。

### Heal Interaction

回復スキルまたは回復アイテムの適用を入力にする相互作用。回復量をそのままアノマリーの HP に加えることを意味しない。

例として、`GIANT`（Mad Stomper）では Heal 系スキルで鎮静状態へ移行する案がある。Healで鎮静できることを全アノマリーに通用する規則とするかは未確定である。詳細は [Mad Stomper](../anomalies/mad-stomper.md) を参照する。

### Skill Interaction

スキル発動を、スキル名ではなく必要なら効果分類・対象・結果文脈で受け取る相互作用。例として、移動、遮蔽、回復、探知、状態変更などを個別に扱える。

スキル効果の共通メタデータは現時点で未設計である。個別スキル ID に直接依存する必要がある場合は、その依存を明記し、汎用化を装わない。

### Item Interaction

アイテムの所持、使用、提示、配置、受け渡し、破棄などを入力にする相互作用。アイテムの真の用途や価値は世界観上不明であり得るため、UI が正解を直接示す前提にはしない。

`Memory Swapper` の所持品・識別への干渉はこの分類と関係するが、現在の `ItemStack` は未実装である。詳細は [Memory Swapper](../anomalies/memory-swapper.md) を参照する。

特定アイテムは、個人だけへの効果ではなく、Run全体のアノマリー出現コンポーネントを変動させ得る。対象には個別出現確率、同時出現数などが含まれ得る。この変更はサーバーがRun状態として確定し、Run終了時に破棄する。具体的なアイテム、変更可能なコンポーネント、重ね方は未決定である。

### Combat / Result Interaction

攻撃・ダメージ・ノックバックなどの通常結果、またはその結果が不成立になることを扱う相互作用。アノマリーが戦闘で倒せることを前提にしない。

`/dev/null` は入力ではなく結果の不成立を主題にするため、攻撃・スキル・アイテムなどの結果を傍受・無効化する設計候補として扱う。どの結果まで影響するかは [/dev/null](../anomalies/dev-null.md) の個別資料で確定する。

### Environment Interaction

マップ状態、ポータル、時間経過、近接、地形、他アノマリー、パーティ状態など、プレイヤーの単発操作ではない世界側の変化を入力にする相互作用。

既存の近接 `Observer` は Exposure を蓄積する環境・近接ベースの仕組みであり、視覚的 Observation Interaction と同一ではない。必要なら両者を一つのアノマリーで組み合わせられる。

## 受理と結果の設計

各アノマリーは Interaction Kind ごとに、少なくとも次のいずれかを取れる。

| 振る舞い | 意味 |
| --- | --- |
| Ignore | 相互作用しない。通常のアクション結果だけが残る |
| Accept | 前提を満たす場合、定義済みの状態変化を起こす |
| Transform | 効果や対象、情報の意味を変換する |
| Intercept | 通常結果が成立する前後に傍受する |
| Reject | 明示的に成立しない。世界内のフィードバックを検討する |

「何も起きない」は有効な結果になり得る。ただし、プレイヤーにバグと区別不能な沈黙だけを返すかどうかは、個別アノマリーの意図として検討する。

## クライアントとサーバーの責務

- 通常のスキル・アイテム・戦闘は既存のサーバー検証済み経路を起点にする。
- アノマリー状態の遷移、報酬、ラン全体への反映はサーバーが確定する。
- アノマリー固有の交換品を相互作用の結果として出現させる場合、同一Runで成立条件を満たしたパーティ全員へ配分する。切断者・不在者の扱いは個別の配分仕様が必要になるまで未決定とする。
- クライアントは視覚・音響・局所的な観察証拠を提示できるが、それだけで共有状態を確定しない。
- Observation Interaction のクライアントカメラ利用とサーバー再検証は、[観察・認識システム](observation-and-recognition.md) の責務とする。
- 個人だけに現れる認識差と、パーティ全体へ影響する状態変化は Scope を明示して分離する。

## 既存資料との対応

| 資料・要素 | 接続候補 | 現状 |
| --- | --- | --- |
| 認知アノマリー | Observation → Recognition、Exposure、認識差 | Draft。判定基盤は共通観察資料へ分離済み |
| `GIANT` / Mad Stomper | Heal → 鎮静候補、花の胞子の出現 | Draft。名称・対応は確定、鎮静条件と専用スキル効果は未確定 |
| `/dev/null` | Combat / Skill / Item の結果傍受 | Draft。対象範囲・優先順位は未確定 |
| Memory Swapper | Item と Recognition への干渉 | Draft。所持品基盤は未実装 |
| `whisper` | Sound / 認知的フィードバック / 非攻撃・非選択 / NPCへの追従先移送 / `anxiety`による対象内発生 | Draft。消失ではなく移送を主要Interactionとし、`anxiety`は潜在要素を持つ対象の状態・エピソードを引き出し得る |
| 近接 Observer | Environment（近接）→ Exposure | 実装メモ上の既存候補。視認判定とは別 |

この表は共通化の出発点であり、個別アノマリーの仕様を確定するものではない。

## 実装の進め方

現時点では共通の `AnomalyInteractionService` を新設しない。二つ以上のアノマリーが同じ Interaction Context と検証・結果処理を実際に共有することを確認してから、最小限の共通ディスパッチを検討する。

当面は以下の順で進める。

1. 個別アノマリー資料に、受理する Interaction Kind と結果を記録する。
2. 既存アクション経路から必要な文脈を安全に取得できるか確認する。
3. 一つの具体的な相互作用をプロトタイプ化し、サーバー検証とフィードバックを検証する。
4. 同じ契約が複数で必要になった場合にのみ、共通実装を抽出する。

## 未決定事項

- Sound Interaction に必要な音源、遮蔽、範囲、同期の最小仕様
- スキル効果を分類する共通メタデータの要否
- アイテム基盤実装後の Item Interaction の対象指定と権限
- `/dev/null` のような傍受系と通常結果・他アノマリーの優先順位
- 複数アノマリーが同じ Interaction Context を受けた場合の競合解決
- 個人・パーティ・ラン全体の結果を混在させる場合の通知と再接続時の扱い
- 意図的な曖昧さを壊さず、失敗・無反応をプレイヤーに伝える表現
