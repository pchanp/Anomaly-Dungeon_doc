# 自動検証と人間レビュー

**Status: Draft（機械検証の通過は採用ではない）**

## 自動検証のエラー

- スキーマ違反、必須項目欠落、空欄、プレースホルダー、未知のEffect種別。
- RUN_ID、担当、予約ID、主対象マップ、分類の不一致。重複ID・ファイル名。
- 未予約IDへの参照。予約済み未作成はエラーにせずレビュー事項。
- snapshotにないMD、Status宣言不一致、パック／snapshotのハッシュ変更。
- 必須sectionやSVGの欠落、SVGのXML構文、外部表示依存、ローカルリンク切れ。
- manifest・HTML・JSONの組み合わせ不一致、stage別の不足件数・分類。
- Aの共通モブ要件、Bの10経路、Cのレベル1〜3など担当の必須構造欠落。
- 機械的に同じJSON本文の候補。類似案の意味的な重複は人間が確認する。

検証器はJSON Schemaのこのパックで使用するキーワードを標準ライブラリで評価する。任意のJSON Schema実装ではない。未対応キーワードを黙って無視せずpack-onlyでエラーにする。

## 自動検証のレビュー事項

- 予約先の未作成、ref解決状況の未確認、性質の不一致、未指定の接続要求。
- `data_dependency` の循環は「採用後の起動を止め得る依存」として報告。`interaction_loop` の循環はゲーム内ループとして別報告。再帰発動の上限や終了条件は人間が確認する。
- proposedなコンポーネント、catalog上未実装／未確認の必要処理、requires_code unknown。
- 候補が申告した既存仕様との矛盾、未確定事項、コスト、表示未確認。
- 文字列として候補に書かれた世界観整合性は機械で保証できない。

## 朝の内容レビュー

人間または別のレビューセッションが本文と図を読む。次を確認する。

1. 根拠MDから仮説までの飛躍が明示されているか。
2. 実装済み・設計済み・草案・Idea・未確認を取り違えていないか。
3. 現実日本の固定、既存作品の転写、起源／正体／博士の真意の断定、型の混同、新地形の確定がないか。あれば差し戻す。
4. 異化したものと世界内で成立し得る理由があり、理由が正典の創作になっていないか。
5. 各案に異なる判断と代償があるか。名称・倍率・マップだけ違う複製を除く。
6. 図が作用を説明し、本文やJSONと矛盾していないか。実ブラウザで読めるか。
7. required_traitsと相手の案が一致するか。起動循環とゲーム内ループの扱いが適切か。
8. requires_codeと試作コストの根拠は妥当か。現行2マップRunに組み込むなら別途何が必要か。

採用／保留／却下は朝の管理側のレビュー記録で付ける。夜間候補の `review_status` は `unreviewed` に固定する。採用後も、このパックのschema通過だけでゲームへ投入しない。統合セッションが実構造と比較し、採用したものだけを別作業として実装する。
