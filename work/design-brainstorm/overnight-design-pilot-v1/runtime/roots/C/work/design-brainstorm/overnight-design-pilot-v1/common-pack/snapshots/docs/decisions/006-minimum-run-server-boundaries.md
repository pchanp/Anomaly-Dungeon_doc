# 006: 最小Runの実装で確定したサーバー境界

**Status: Draft（草案）**
**Date: 2026-09-29**

## 背景

[005: 都市ロビーから開始する最小Runの範囲](005-minimum-lobby-run-scope.md)の範囲を実装した。005は仕様側、006はそれをコードに落としたときに決めた境界だけを扱う。005の判断は変更していない。

実装中に、005が「実装前になお必要な詳細」として挙げていた項目について、実装判断が必要になった。判断できたものは実装し、できなかったものは未確定として残す。

## 現時点の判断

### 状態の置き場所

- Runの状態は `RunService` が保持し、`AnomalyState:RunState` と `M.GetRunState()` の両方から同じ値を返す。`AnomalyState` は既存の状態受け渡し先だったため、Runの新しいAttributeを別の器に分けなかった。
- プレイヤーのロビー帰属は `LobbyState` 属性で持つ。都市ロビー、入口ロビー、パーティ受付中、探索中、リザルト、の5値。
- 既存の `InDungeon`、`PlayerRunState`、`QuestState`、`QuestObjective`、`Room`、`Credits` は削除しない。Runの開始と終了でまとめて更新する二重の意味を持たせる実装にした。専用データモデルへの移行は将来的な課題として残す。

### 終了種別の集約

- すべての終了を `RunService.Finish(player, outcomeId)` に集約する。種別と成功／失敗フラグは `Shared/Definitions/RunOutcomes` が持ち、ラベルもそこから送る。
- クライアントは成功／失敗の判定を一切持たない。`Result` で受け取った値だけを画面に出す。

### ロビーの実体

- 都市ロビーとダンジョン入口ロビーは、生成ダンジンモデルとは別の常設Runtimeモデルとして作る。生成マップはRunの開始時だけ生成し、終了時に破棄する。
- 各マップ内の `world.Lobby` は都市ロビーではない。生成マップのLobbyはマップ構造の一部として扱い、Run終了の帰還先には使わない。
- 位置と受付条件は `Shared/Config/LobbyConfig` に置く。現時点の配置は機能検証用で、都市構造の決定ではない。

### 入口の認可

- 生成マップ内 `LOBBY/GimmickPoints/Enter` のTouch入場は、パーティ受付を迂回するため撤去した。`LobbyDungeonEntranceFix` は無効化し、入場を `PartyService` の受付と `RunService.StartRun` だけが認可するようにした。
- `RunService.Enter` は出発済みパーティ以外を受け付けない。残したのは、生成マップ側のプロンプトが依存しているため。

### デバッグ経路

- `DebugMapSwitch` は `RunState` が `IDLE` でない間マップを受け付けない。正常Runの候補抽選とは別の経路として保つ。
- デバッグフロアは初期配置とTick対象をフロア内へ限定した。都市ロビーへの初期配置は `RunService` が担う。Run中のプレイヤーへRun Lifetimeや状態リセットが干渉していたため。
- アイテムは `DebugInventoryTerminal` のデバッグ付与でしか作らない。正式な取得源が無い状態で、アイテムの創作を実装の都合で増やさない。

## 005仍然として未確定の項目

- 異常化後のRun Lifetime満了の扱い。最小版では失敗として扱い、基本報酬を支払わない。生存したまま失敗が確定する経路になるため、帰還手段と生存報酬を含めて別途決める必要がある。
- マルチプレイヤー向けのサーバー割当、並列Run、再接続、サーバー間移動。実装していない。
- Secure Slotの拡張手段、拡張上限、コスト、入出庫タイミング、Player Anomaly時の制約。
- リザルト画面での獲得物・喪失物の表示詳細と、保持Questを複数持つためのデータモデル。
- マップ抽選のseed表示と再抽選可否、将来の重み付けの可視化。
- 都市ロビーのSpawn位置とロビー構造の確定。

## 判断理由

- 生成ワールドをRunの生存期間に一致させることで、8月31日の時計と環境状態が次のRunへ持ち越されないことを構造で保証した。
- 終了を1つのAPIに集約することで、成功・失敗・獲得物・喪失物の関係を1か所で編集できるようにした。クライアント表示の創作を排し、仕様を偽装しない。
- 生成マップの入場経路を1つに絞ることで、005が禁じた「進行中Runへの途中参加」を構造的に防ぐ。
- デバッグ経路と正常Runの経路を `RunState` で分離し、デバッグ用マップが正常Runの候補抽選に混ざるのを防ぐ。

## 影響

- 起動直後は `AnomalyDungeon` モデルが存在しない。デバッグフロアから `DebugMapSwitch` で読み込むか、入口ロビーの受付から出発する。
- 生成マップの `Enter` プロンプトは使わない。入口ロビーのパーティ受付が唯一の入場経路になる。
- マップ生成は `PartyService` の受付ループではなく別スレッドで走らせる。同一スレッドで走らせると、受付ループの実行予算と合算して script timeout になる。
- 生成ワールドのない状態で `DebugMapSwitch` を使う経路は従来通り利用可能だが、`AnomalyDungeon` 内に生成されるプロンプトは動かない。
