(b) 設計仮説とプレイヤーの選択

設計仮説: 誰も回収に来ない廃店舗に、返却を待つ人が1人だけいる。この人がその場所にいる理由は、借りた1本を返却しに来ることです。店のことや世界のことは説明しません。棚を調べて得られる選択結果の中に、その1本だけが依頼の対象として印付けられる。印は新しい正解表示として作らず、既存のArchive Selection UIの結果状態に持たせます。渡すと、その項目は渡したプレイヤーの個人試聴の候補から外れます。放置しても成立し、攻撃は解答として設計しません。地形、部屋、正式配置は追加しません。

狙う体験

同じ「調べる」操作の先に、具体的な目的が一つできる。そして手放すことを許される。印は理由の説明をしないため、渡すべきものかどうかは依頼主の要求から判断するしかない。

判断と代償

先に自分で試聴する／NPCへ渡す／印を考えず別の棚へ時間を使う／位置変化だけ見る。渡すと自分の確認手段を失う。放置しても印はRun中残り、NPCは帰還まで待つため手掛かりは失われない。誰が先に調べたかで先手と後手の結果が違う。

作用図 — 印は個人提示、渡しは自分の試聴経路を1つ消す

この図で分かること: 印（情報提示）、除外（入力結果の無効化）、退場（個体状態）が別の結果として分かれる。試聴候補の除外は当該個人だけの変化である。

図では確定しないこと: 対象の棚の位置、印の件数、移動の周期と地点、印の説明を出せるか。図は作用と選択の模式的表現であり、室内の正式な配置図ではない。

(c) Trigger・Condition・Effectの契約

Effectは3件。印は情報提示、除外は入力結果の無効化、退場は個体状態として分ける。

Effect 1: InformationChange持続（sustained）／保存境界: 同一Run中／依頼対象の印
Trigger対象が棚を調べ、Archive Selection UIを開いて項目を1つ選び、その項目が依頼対象である条件を満たす。
Condition依頼がRun開始時点で有効であること。選択結果に対象項目が含まれること。対象が通常のプレイヤーであること。対象項目は名前と選択結果だけを持ち内容は閲覧できない。
結果選択結果の表示に、依頼対象である印を付けて個人提示として返す。印は目的だけを明確にするもので、理由や正体は説明しない。
対象・作用範囲対象: 選んだ個人。範囲: 個人。同じ項目でも印を得た個人ごとに独立して成立する。
保存境界・終了終了条件: 依頼を成立させた／Run終了／マップ終了。いずれかが成立すれば閉じる（any）。依頼成立で印が消えるのは、処理が済んだという結果の手掛かりである。
重ね掛け例外ではない。同一Effectかつ同一対象は非加算1件。同じ項目を再度選んでも印の状態は重複しない。同じ選択結果へ別の印を載せる処理は本候補の範囲外であり、競合規則は未定義のため保留。
Server / ClientServerが依頼の有効性、選択結果の対象項目、対象属性、所持状態を検証し、印をクライアント側の推測で表示しない。Clientは選択結果の印のみを表す。
Feedback成功: 印が付き他項目と区別できる。失敗: 印が付かない（対象以外を選んだ、または依頼が無効）。判別不能: なぜ対象なのか、渡すと何が変わるのかは説明しない。
Effect 2: RuleOverride持続（sustained）／保存境界: 同一Run中／個人試聴の候補からの除外
Trigger対象項目をNPCへ渡す操作が成立した。
ConditionServerが対象項目の所持、距離、NPCの個体、依頼状態を検証して成立を確定した場合。所持が無い、相違する対象、NPCが退場済みの場合は成立しない。
結果当該個人の個人試聴の候補から、その項目を外す。選択も再試聴もできなくなる。同じ項目が他個人の候補に残ることは妨げない。
対象・作用範囲対象: 渡した個人の所持と、個人試聴の入力判定。範囲: 個人。共有BGMや他個人の試聴には影響しない。
保存境界・終了終了条件: Run終了／マップ終了のみ。Runをまたいで残さない。戻す手段は本候補に含めない。
重ね掛け例外（true）として、同じ項目を複数回渡しても記録は個人ごとに1件で二重に加算しない。優先順位: 個人試聴の入力判定より先に適用する。共有BGMの選択処理とは独立であり、どちらの順でも影響しない。出現計算に作用しないため博士Questの補正や発生ごとの減衰とは競合しない。
Server / ClientServerが距離、所持、NPC個体、依頼状態を検証し、成立しない操作では除外しない。Clientは候補から消える表現のみ。理由の説明は出さない。
Feedback成功: 渡した直後に候補から消える。失敗: 渡せなければ候補は残る（理由の区別は提示しない）。判別不能: 消えた項目は試聴できないため、失った情報の意味は本人にも分からない。
Effect 3: StateChange持続（sustained）／保存境界: 同一Run中／NPCの待機、移動、退場
TriggerNPCが現在位置から別位置へ移る、または依頼成立で店から去る。
ConditionNPCがRunに存在し、依頼が未成立である間だけ移動する。依頼成立後は退場のみ。
結果個体の状態が待機、移動、退場のいずれかへ移る。移動は位置の変化としてのみ他のプレイヤーにも見え、依頼の内容は共有しない。
対象・作用範囲対象: NPCの個体（Server Run共有）。範囲: Run共有の個体。位置は全Clientに表現されるが、依頼の印は個人である。
保存境界・終了終了条件: 依頼を成立させた（退場）／Run終了／マップ終了。退場の条件は依頼成立のみであり、放置では退場しない。放置も成立する設計とする。
重ね掛け例外ではない。同一個体の状態遷移はイベントごとに1件。同じ個体へ他の状態異常が重なる場合の順序は共通既定に従い、規則がない競合は保留。
Server / ClientServerが個体の存在と依頼状態を検証し、退場済みの個体には遷移させない。Clientは移動表現のみ。依頼対象の知識は伝えない。
Feedback成功: 位置が変わり、どこを待っているかが痕跡として分かる。失敗: 依頼成立後は再出現しない。判別不能: なぜその棚で待っているのかは本人にも分からない。

(d) 未確定事項・矛盾・異化と留保

未確定事項返却待ちの対象項目は1つだけとする案だが、印を1件だけ持たせるのか複数持たせるかは未定。対象の棚を固定するかRun開始時に選ぶかは未定で、本候補は固定しない。印を説明しない前提だが、説明を出さないと成立が読めない場合の別ルートは未検討。NPCが攻撃を受けた場合の挙動は設計していない（逃走か無反応かは判定していない）。店内を往復する周期と地点の数は未定。依頼がRun開始時点で無効な場合に印を出すべきかは未検討。正式なItemStackは未実装であり、所持の扱いは仮である（SRC-01）。
既存仕様との矛盾2件をconflictsに記録している。（1）判断009の「落下ケースと欠番は少数に留める」「既存のArchiveShelfと追加の視覚棚を混同しない」に対し、本候補は欠番を視覚効果ではなく選択結果の状態として扱う。（2）map-gimmick-ideasにはBack Roomなどで再生すると共有BGMを変えられる案があるが、本候補は共有BGMを一切変更しない。
補正と理由欠番の見た目も数も落下物の量も増やさず、追加するのは選択結果に保持される状態の欄だけとする。棚の視覚構造は増やさない。個人試聴が共有BGMを変えないという実装済みの境界は崩さず、共有BGMを変更する操作は本候補に含めない。いずれも判断009と実装済みの挙動を壊さないため補正可能と考える。ただし既存UIの構造変更の可否は判断を要する。
異化したもの判断009が廃店舗を閉店直後のアーカイブとして残す判断を踏襲しつつ、そこに待つ人を1人だけ置くことで、静かな探索へ人の目的を一つ差し込む点が異化である。目的のない店ではなく、目的だけがある状態を提案する。
世界内の成立理由舞台設定は、レジや会員端末のような古い機械と紙のレシートが混在する文明を想定する。借りたものを返しに来る、という取引の手順は、この場所が異常な空間へ変わっても成立する。誰が借りたのか、店は今も開いているのか、返却に何の意味があるのかは説明しないため、NPCは世界の説明役にならない。
曖昧に残す意味なぜその人が閉店した店へ来たのか、なぜ返却が必要なのか、店とメディアの関係はどこまでなのか。印は目的だけを示し、理由は示さない。世界の起源、アノマリーの正体、博士の真意には触れない。

(e) 他担当への接続

接続タグ: NPCState / Item / Present / ArchiveMedia / Interaction / InformationSharing

使用するコンポーネント: catalog: NPCState、ArchiveMedia、Effect.InformationChange、Effect.RuleOverride、Effect.StateChange。proposed: NpcRequestMarker。catalogのIDは記述語彙であり、実装を保証しない。

他候補へ提供できる性質: 個人提示で依頼対象を明示できる（目的だけを明確にし、理由は説明しない）／提示の成立によって個人の入手経路を1つ失わせられる／NPC個体の位置変化がRun共有の痕跡として残る／共有の事実と個人の表示を分離して扱える。

予約参照ROLE-B-004（data_dependency、resolution: reserved_unresolved）。要求する性質: 棚の選択結果を個人の所持対象として区別できる／所持の成立と喪失を個人単位の状態として扱える。代替: B側の候補が成立しない場合、印の提示とNPCの待機、移動、退場は成立したまま残り、個人試聴の候補から除外するEffectは保留して試聴の可用性を下げない。
予約参照ROLE-C-004（optional_connection、resolution: reserved_unresolved）。要求する性質: 戦闘をしない介入として提示を扱える（非攻撃の操作だけで依頼を成立させられる）。代替: 接続がなくても成立する。近づいて渡すと通常の近接操作だけで成立し、Cの候補が無くても結果（印、除外、退場）は同じである。
未解決の理由B-004: 正式なItemStack、取得源、所有者規則は未実装（SRC-01）であり、棚の項目を個人所持できるかどうかはB側の設計に依存する（adoption_blocker: true）。C-004: Cの候補は未配布であり、Cが戦闘以外の提示操作を定義するかは不明。いずれも要求する性質の語彙だけを記し、相手の内容を創作していない。
ID未指定の要求Archive Selection UIに選択結果の状態を保持する欄を追加してよいか（既存UIの構造変更の可否）。依頼対象の棚を固定するかRun開始時に選ぶか。いずれも候補IDでは特定できないため共通設計側の判断が必要（adoption_blocker: true）。
予約IDは未作成であり得ます。peer-snapshotsが配布されていないため相手の本文を読んでいません。存在しないページへのリンクは置いていません。

(f) 新規ロジックと試作コスト

requires_code: true — 既存のTSUTAYAには通常NPCの状態機械、依頼状態、所持と結び付いた提示除外の経路が存在しない。メディア項目は名前と選択結果のみを持ち、正式なItemStackは未実装（SRC-01）である。NPC個体の移動と退場、選択結果への印の保持、除外判定という3経路はいずれも新規実装を要する。コード生成の許可ではない。

新規ロジック: 通常NPC1体の店内移動と退場の状態機械／依頼対象の状態を保持する欄と個人提示へ落とす経路／所持済みの対象項目を個人試聴の候補から除外するRuleOverrideの判定／提示成立、除外、退場のServer検証（距離、所持、NPC個体、依頼状態）。

試作コスト: 中。 NPC1体と既存UIへの1列の追加に限定すれば中程度。ただし既存Archive Selection UIへ状態欄を足せるか、正式な所持基盤が無い状態をどう扱うか、5基の棚のうち対象をどう選ぶか、は試作前に決める必要がある。判断009は棚と照明で視界が分断される構造と、棚の追加PartおよびPointLight数がクライアント負荷へ影響することを検証項目として挙げている。配置と負荷は未検証。実時間の見積もりは出していない。

想定する既存部品: 5基のArchiveShelfとArchive Selection UI（一覧、選択、閉じる）／個人試聴機3台と、試聴が自動終了するPreviewDuration／共有BGMのServer State（個人試聴では変わらない）／FRONTのレジ、会員端末、販促面（判断009の基準状態）／Server権威のPlayer Anomaly属性と判定。

(g) 担当固有（ROLE-A）の記述

NPCの目的借りた1本を返却しに来る人。目的はそれだけで、店のこと、アノマリーのこと、自分がなぜそうしているかの説明はしない。依頼主ではなく客の立場で、自然にある所作だけをする。移動は位置の手掛かりとしてのみ機能させ、依頼の内容を教える役割にはしない。個体数は1体で、放置してもRunは閉じない。世界設定やアノマリーの起源を説明する役にはしない。
具体的な選択個人試聴機へ持ち込んで先に確かめる／NPCへ渡して成立させる／印の意味を考えず別の棚や端末へ時間を使う／位置変化だけを見る。印は理由の説明をしないため、渡すべきものかは依頼主の要求から判断するしかない。誰が先に同じ棚を調べたかで結果が変わるため、Partyでは同じ結果にならない。
Player Anomalyの扱い判断019によりPlayer Anomalyは通常NPCとInteractionできないため、印の提示も依頼成立も享受できない。依頼の成立は通常プレイヤーのみが行える。印は個人単位なので、他のプレイヤーが先に成立させた結果は他の個人の表示に留まる。Player Anomalyが成立済みの項目を引き継ぐかは未確定であり、異常化によって依頼が失われる以外の処理は発生させない。
mob_contract: 対象外spawn_condition: 通常NPC1体（客）のみであり、モブ敵の発生を含まない。イベントから通常モブが生まれる契約はROLE-A-013で扱う。／population_cap: 個体数は1体固定で湧きも補充も持たない。上限と湧き枠の扱いはROLE-A-013側だけに置く。／non_combat_response: 戦闘を設計していない。攻撃は解答にならず、印も依頼成立も発生しない。逃走か無反応かは判定していない。／exit_condition: 退場は依頼成立とRun終了のみ。放置が退場にならない点が設計上の要点。／entity_distinction: 通常NPCでありAnomaly EntityでもPlayer Anomalyでもない。Interaction KindはPresent（受け渡し）と近接の観測のみ。whisperの追従先移送の連鎖とは接続しないため、移送は発生しない。
